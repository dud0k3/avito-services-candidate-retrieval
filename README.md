# Кандидатогенерация объявлений услуг

Задача: вернуть до 50 объявлений для каждого поискового запроса. Качество
оценивается по Recall@50: попало ли объявление, выбранное пользователем, в эти
50 кандидатов. Порядок внутри списка на метрику не влияет.

## Подход

Я использовал четыре текстовых сигнала:

1. TF-IDF по словам и парам слов в заголовке объявления.
2. TF-IDF по символьным фрагментам заголовка (3–5 символов). Он помогает с
   разными формами слов и мелкими опечатками.
3. TF-IDF по заголовку, параметрам и началу описания. Заголовок повторён
   дважды, чтобы длинное описание не вытесняло название услуги.
4. TF-IDF по фильтрам запроса и параметрам объявления. Например, выбранный
   пользователем вид услуги можно сопоставить с видом услуги в объявлении.

Каждый сигнал предлагает до 150 объявлений по всему корпусу и до 150 из
локации запроса. Затем кандидаты объединяются и получают взвешенную сумму
сходств: 0,285 для слов в заголовке, 0,240 для символьных фрагментов,
0,225 для полного текста и 0,250 для фильтров. Сначала берутся лучшие
объявления из локации запроса; если их меньше 50, оставшиеся места занимают
объявления из других локаций. В обучающих парах около 83% выбранных
объявлений имеют тот же `location_id`, что и запрос. Такая сильная ставка на
локацию дала лучший Recall@50 на локальной проверке, хотя иногда может
пропустить подходящее объявление в соседнем городе.

`search_category` почти всегда равен 114, а флаг доставки в запросах
бенчмарка всегда нулевой. Поэтому они не участвуют в итоговом скоре.

Решение использует только `pandas`, `NumPy`, `SciPy`, `scikit-learn` и
`PyArrow`. Предобученных моделей и внешних API нет.

## Локальная проверка

Я взял 600 случайных уникальных сочетаний признаков запроса из `train.parquet`
с фиксированным seed 42. Релевантными считал все уникальные `item_id`,
выбранные по такому сочетанию. Корпусом были все 344 825 уникальных объявлений
из `train.parquet`. Это позволяет проверить Recall@50: большинство выбранных
объявлений из `train.parquet` отсутствует в `benchmark_items.parquet`.

Первый вариант без сигнала фильтров дал Recall@50 **0,7167**. После добавления
фильтров и выбора весов результат вырос до **0,7509** на той же проверке.
На второй выборке из 300 запросов с seed 123 итоговый вариант дал **0,7006**,
а вариант с нулевым весом фильтров — **0,6689**. Это локальные оценки, а не
результат на скрытых запросах бенчмарка. Корпус для проверки также больше
бенчмарк-корпуса, поэтому числа не обязаны совпадать.

На примерах ошибок видны два случая. Иногда подходящее объявление находится
среди нескольких сотен кандидатов, но не входит в финальные 50. Иногда оно
вообще не попадает в текстовую выдачу: запрос и объявление описывают одну
услугу разными словами, например «снять беседку» и «аренда беседки». Для
следующего улучшения я бы проверил расширение запроса или локальную модель
эмбеддингов, а затем сравнил прирост Recall@50 и время работы.

## Запуск

Нужны три Parquet-файла в одном каталоге: `train.parquet`,
`benchmark_queries.parquet`, `benchmark_items.parquet`. Данные в репозиторий
не включены.

```bash
python -m pip install -r requirements.txt
python retrieval.py --data-dir /path/to/data --validate
python retrieval.py --data-dir /path/to/data --output answer.csv
```

Второй запуск создаёт `answer.csv` без индекса и проверяет состав запросов,
допустимость `item_id`, отсутствие повторов и ограничение в 50 кандидатов.
Для повторения основной локальной проверки параметры `--validation-queries 600`,
`--seed 42` и `--local-quota 50` совпадают со значениями по умолчанию. Для
второй выборки использовались `--validation-queries 300 --seed 123`.
